# 短影音成效審查

**觸發時機**：`out/final.mp4`（或 mastered 版）已存在、尚未交付／發布。
**產出**：一份可逐項接受／退回的修改提案，餵回 `video-magician` 的 config。

這個 skill 的價值全部建立在**它敢說不知道**。任何一句沒有證據的話都會讓整份報告變成
安慰劑——寧可少講，不要編。

---

## 證據分級（每一條結論都必須標）

| 級 | 意思 | 例 |
|---|---|---|
| `[A]` | 從產物機械算得出來，不含判斷 | 「第一句人聲在 1.23s」 |
| `[B]` | 看片＋讀逐字稿後的編輯判斷，可爭辯 | 「這個 hook 只講了發生什麼，沒講干我何事」 |
| `[C]` | **本質上不可知**，禁止宣稱 | 觸及數、留言數、會不會爆、會紅在哪些圈子 |
| `[EXT]` | 平台當下的官方行為，**不等於**成效預測 | 「Spotlight 滿 30s 才能營利」 |

**寫報告時 `[C]` 一律進 `unknowns` 區塊，不准偽裝成結論。**
使用者「留言驅動觸及」的假設要記成**我們正在最佳化的策略**，不是已證實的因果。

---

## 工作流程（四關，順序不可調）

```
1. 確認 Hook        → 量 + 看，給 strong / repair / absent
2. 判定對話驅力      → conversation_ready / edit_can_create_conversation / footage_needed
3. 產出修改提案      → 標好 apply_mode，餵回 video-magician
4. 跟使用者逐項討論   → 接受才動手，絕不自己套用
```

### 第 0 步：機械量測（必跑，不可跳過）

```bash
node tools/analyze_signals.mjs --video out/final_mastered.mp4
```

它輸出的全是 `[A]`：規格、時間軸、Hook 視窗、無聲可讀性、閱讀負荷、空檔候選、
剪點分佈、overlay/運鏡/SFX 清單、疊加密集處、首尾幀差。

**它刻意不評分、不排名、不預測**——它的工作只是**指出哪些時間點值得你親自看**。
拿到數字後**一定要真的抽格看那幾個時間點**，不能只讀數字就下判斷。

⚠️ 讀數字的三個陷阱（工具輸出裡也有提醒）：
- `CONFIG.cuts` 是**被移除的來源區間數**，不是鏡頭數。別叫它「shot count」。
- **空檔 ≠ 廢話**。可能是畫面自帶音效、示範畫面、或刻意留的笑點節拍。先聽再說。
- 疊加密集不等於雜亂。笑點本來就該多層強化，看了再判。

### 第 1 步：確認 Hook

用巢狀視窗看「觀眾到第 N 秒為止**實際收到**什麼」（工具已算好）：

| 視窗 | 該完成的事 `[B-heuristic]` |
|---|---|
| 0–0.8s | 有沒有一個中斷——畫面或聲音上的意外。封面若吃掉這段，封面就得自己當 hook |
| 到 1.5s | 觀眾能用一句話說出「這在講什麼、卡住什麼」 |
| 到 3s | 承諾／疑問／風險／矛盾成立 |
| 到 5s | 出現**證據或反應**，證明後面真的會兌現 |

記錄：`hook_text` / 來源與輸出時間 / `subject` / `tension` / `promised_payoff` /
`first_evidence_output_sec` / **無聲版等效**（靜音看得懂嗎）/ verdict。

**「有 hook」和「hook 夠強」是兩個判定**，分開寫。

常見失敗（詳見 `references/hook-failures.md`）：只講發生什麼不講干我何事、
解釋跑在衝突前面、代名詞先於指涉物、無證據的最高級、封面稅、
標題與口白承諾不同件事、靜音就看不懂、**hook 有懸念但沒留下可爭辯的東西**。

### 第 2 步：對話驅力（**最重要的一關**）

先讀 `references/conversation-mechanics.md`，那裡有七種機制與逐條檢查。

**判定不是「有沒有叫人留言」，而是能不能明確回答這三件事：**
1. 觀眾**在回答什麼**？（回應對象要具體）
2. 為什麼**至少兩種答案都站得住**？（只有一個正確答案＝沒得聊）
3. **在哪一秒**被邀請？看到足夠證據了嗎？停留夠久能想完嗎？

七項全過才算 `conversation_ready`：回應對象明確／一句話能回／至少兩種說得通的答案／
問之前已給證據／提示停留夠久／結尾沒把話講死／不是「留言 1」「tag 三個朋友」這種假互動。

三種判定：

- **`conversation_ready`** — 說出觀眾會回什麼、為什麼會分歧。
- **`edit_can_create_conversation`** — 先提**只靠剪輯**的誠實解法：把判斷題移到證據旁邊、
  縮短兌現後的尾巴、把封面改成真正的選擇題、讓爭議點多停留 1–2 秒。
- **`footage_needed`** — 素材裡**根本沒有**選擇、分歧、失敗、代價、意外或觀眾可代入的經驗。
  這時**必須明講缺哪一種機制、需要什麼素材**，例如：
  「有沒有一段是你不同意它的判斷、或它挑錯、或你手動改回來的畫面？
  那會補上『評價／分歧』機制。」
  **不要假裝剪輯能生出不存在的東西。**

🚫 **硬約束：不准為了製造問題而改 `src/subtitles.json`。**
字幕是本人講過的話（正典），把它改成他沒說過的提問是造假。
要加提問只能走 **overlay / 片尾卡 / 補拍新素材**。

### 第 3 步：節奏與平台

節奏門檻與平台事實在 `references/platform-targets.md`。原則：

- 指標只用來**定位要看的視窗**，不用來判定好壞。看了才算數。
- **「流暢」＝念頭的連續性**，不是快。每一段都要有：給資訊／給證據／換情緒／
  刻意的節拍，四者之一。純粹加快不會變流暢。
- 平台差異只在**有具體編輯理由**時才做變體，不要為了湊數字生一堆版本。

### 第 4 步：提案與交付

每條 finding 必須有：`claim` / `evidence`（檔案＋欄位＋時間範圍）/ **`falsifier`**
（什麼情況下這條就不成立）/ `observable_goal`（改完可觀察到什麼，**不是**「留言會變多」）。

每條提案必須標 **apply_mode**：

| mode | 意思 |
|---|---|
| `config_patch` | 改 `videoConfig.ts` / 字幕時間即可（cuts、speed、封面、運鏡、overlay、SFX、bgm.ducks、outro） |
| `source_rebuild` | **需要重建 `public/source.mp4`**（見下方硬限制） |
| `footage_request` | 沒有誠實的剪法能做到，要補拍 |
| `schema_blocked` | config 沒有這個欄位（例如任意座標的 overlay），要先擴充引擎 |

⚠️ **引擎硬限制：`CONFIG.cuts` 只能「移除」，不能「重排」。**
`src/engine/cuts.ts` 永遠按來源時間順序輸出保留段。所以「把爆點移到最前面」
**不是** `config_patch`，而是 `source_rebuild`（重建合成來源＋所有 cue 時間重定基準），
或用「成品後製接片」（從 render 抽該段貼到最前，再重新 mastering）。
**絕對不要把它標成 config 改動**，那會讓剪輯端做不出來。

輸出格式：一份 JSON（schema 見 `references/output-schema.md`）＋給人看的一張表：

| ID | 改什麼 | 為什麼 | mode | 決定 |
|---|---|---|---|---|
| edit-001 | … | … | config_patch | 接受／退回／修改 |

**接受的提案才進 `video-magician` 套用 → 重渲染 → `make_review.mjs` 既有審核閘門。**
成效提案先獨立成 `out/performance.json`，不要塞進 `review.feedback.json`
（`make_review.mjs` 目前不吃 `perf-*` id）。

## 拒絕清單（硬約束，不是建議）

這個 skill **不做**：

- 預測觀看數、觸及、留言數、漲粉、「會紅在哪幾個圈子」`[C]`
- 宣稱留言會「導致」演算法推播，或描述未公開的排序內部機制 `[C]`
- 製造假爭議、假失誤、羞辱性提問、刻意誤導式懸念
- 拿「留言 1」「tag 三個朋友」充當對話機制
- 把字幕改成本人沒說過的話 `[A/B]`
- 把「重排素材」講成 config 改動 `[A]`
- 把剪點數當鏡頭數、把字幕空檔當已確認的廢話 `[B]`
- 為了湊密度數字砍掉反應、示範、情緒鋪陳或笑點節拍
- 為了「特效太少」而加特效
- 在使用者接受之前自己動手改
- 繞過 `review.html` 的逐項人工閘門
- 在沒有真實發布數據前，宣稱某次修改「改善了成效」`[C]`

## 有真實數據之後

使用者若提供實際後台數字，才可以驗證假設，且只能用**觀察到的**量：
留言人數、回覆串深度、提問被回答的比例、被改動視窗前後的留存變化。
**分母缺了就說缺了，不要湊。** 每個版本盡量只改一個機制，結果才解讀得動。
